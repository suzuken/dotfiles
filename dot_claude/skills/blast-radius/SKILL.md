# blast-radius

変更が、出荷前に別の場所で何を壊すかを見つける。

呼び出し元を列挙することは仕事ではない。それは grep で数秒で終わる。
仕事は、grep では見えない壊れ方を見つけることである。

## 説明文を信用しない

もっともらしい影響範囲の説明は、正しくても誤っていても同じように説得力がある。
だから説明文を成果物にしない。変更の安全性が依存している 1〜2 個の事実を特定し、
コードを動かして証明する。

## 確信度の段階

安全性が依存する事実ごとに、手間が見合うところまで下の段階を進め、どこで止まったかを書く。

1. **そう言った。** それだけでは価値がない
2. **該当行を示した。** 実在する `file:line`、またはライブラリのソース
3. **悪いケースが起きないことを示した。** 失敗する経路を一歩ずつたどり、そこに到達しないことを示した
4. **実行した。** 実際のコードを呼び、前提が誤っていれば大きく失敗するスクリプトかテストを走らせた
5. **動いているアプリで再現した。** プロジェクトに検証 skill（`verify-<app>`）があればそれを使う。再現に元に戻せない操作（push、デプロイ、外部への送信）が要るなら、ユーザーの確認なしに実行しない。模擬（一時リポジトリ、`git update-ref` で作った ref、ローカルのスタブ）で段階 4 に止め、止めたことを書く

段階 4 は、多くの場合、アプリが使っているのと同じライブラリを import して、
懸念している関数をそのまま呼ぶ小さなスクリプト 1 本で済む。

## 手順

1. **変更を読む。** diff、追加・変更・削除されたシンボル、変更後に振る舞いがどう変わるかを把握する。diff に書かれていない変化も含める。経緯は `git log -p`、`gh pr view`、関連 PR のレビューコメントから取る。PR がなければ commit メッセージと、同じファイルの過去の commit から取る
2. **安全性を支える事実を 1 つ見つける。** 危険に見える変更の多くは、1 つの事実のおかげで安全である（例: 「この呼び出しは、すでに無効になったキャッシュ項目を捨てるだけで、他には何もしない」）。その事実が成り立てば、危険なケースの大半がまとめて消える。可能性の長いリストを作るより、ここに時間を使う
3. **grep が届かない場所を見る。**
   - 呼んでいるライブラリのソースを読む。lockfile で固定された版と、ローカルのパッチを確かめる
   - 実行の順序を考える。マイクロタスク、unmount や teardown の時点、フレームワークごとの評価順
   - スクリプトや hook なら、呼び出す外部コマンドの版と引数の解釈（空白での分割、クォート）、シェルの違い、環境変数や引数が欠けたときの既定値を確かめる
   - シンボル検索では追えないつながりを追う。API が返す JSON、DB のカラム、ワイヤーフォーマット、同じバイト列を読む別言語のコード、feature flag、3 段先の下流のコード
4. **リスクを正直に見積もる。** 各リスクに、起きる確率と起きたときの損害を付ける。確かめたリスクと、調べて問題なしと判断したものは分けて書く。引用は実在する `file:line` に限る。検索して何も見つからなかったことも結果として書く。呼び出し元や API を推測で作らない
5. **その事実を証明する。** 実際のコードを動かすスクリプトかテストを書いて実行し、出力を貼る
6. **大きい変更、広い変更では意見を分ける。** 目安は、複数のモジュールやサービスにまたがる変更、または安全性を支える事実が 1 つに絞れない変更である。 同じ問いを独立した subagent 2 体に投げ、答えを突き合わせる。モデルが違うと見つかるバグも違うので、2 体には別のモデルを指定する（Agent ツールの `model` に `opus` と `sonnet` など）。両者が独立に挙げたリスクを最も重く見る

## 返すもの

- **変更の中身**：何が変わったか。自明でない部分を含める
- **安全性を支える事実**：事実そのもの、どの段階まで確かめたか、証明の出力。証明できなかったら「未証明」と書く
- **リスク**：壊れ方、`file:line`、確率と損害、確かめ方。重要なものには証明の出力を貼る
- **問題なしと判断したもの**：何を調べ、なぜ問題ないか
- **merge 前にやること**：本当のバグを捕まえる最も安いテストか再現手順。手順 5 で書いたスクリプトを含める
