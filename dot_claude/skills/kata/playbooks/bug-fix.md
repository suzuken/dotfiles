# bug-fix：不具合の修正

出荷するすべての行は、実行して得た証拠で裏付ける。「念のため」の変更は仮説であって修正ではないので、出荷しない。証拠が仮説を否定したら、その仮説に基づいて入れた変更は戻す。

1. 症状が出る経路で、自分で再現する（`verify-<app>`、テスト、CLI）。経路とは、ユーザーが触る入口（UI、CLI、API）のことである。自動テストが同じ入口を叩いていれば同じ経路とみなす。再現できなければ、試した経路と、届かない理由を書く
2. 原因の仮説を挙げる。コードの仕組みと、`git log -S` や関連 PR に残る回帰の経緯を材料にする。探索範囲を最も大きく削れる確かめ方から順に潰す
3. 再現を、失敗するテストにする（Red）。テストの基盤がなければ、失敗する再現スクリプトで代える
4. 根本の地点で、最小の変更で直す。関数の境界をまたぐなら、型と呼び出し側を先に決める。本番で急ぐ不具合なら、まず症状を止める最小の変更を別の PR で出し、根本対策をその後に続ける
5. 同じ経路で再現が通ることを確かめる（Green）。単体テストが通っただけで合格にしない。別の経路での確認も合格にしない
6. 影響範囲を読み切れなければ `blast-radius` を通す
7. 失敗するテストの commit の上に、修正の commit を積む。`ship` に進む

**返答**：何が壊れていたか、根本原因、修正、確かめ方（失敗から成功に変わった出力をそのまま貼る）。
