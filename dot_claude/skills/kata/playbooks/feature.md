# feature：機能の追加と変更

設計が決まっていない、または判断が要る点が残っているなら、先に `design` を通す。

1. 目的と完了条件を一文ずつ書く。issue があれば、その受け入れ条件と対応づける
2. データの形、型、公開シグネチャを先に書く。呼び出し側の使い方から決める
3. 足す前に、削れるもの（使われていないコード、重複）を探す。頼まれていない機能や演出は足さない
4. テストを先に書く（Red）。テストは利用者から見える振る舞いを assert する。実装を書いて通す（Green）。整える（Refactor）
5. 実物で確かめる。UI の変更なら `verify-<app>` などで変更前後のスクリーンショットを取り、ユーザーの立場で操作して違和感がないか見る
6. 複数の PR になると分かったら、`multi-pr` に切り替える
7. `ship` に進む

**返答**：誰にとって何が変わるか、どう確かめたか、証拠の場所、残した課題。
