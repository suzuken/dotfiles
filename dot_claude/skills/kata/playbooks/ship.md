# ship：PR を出して merge できる状態まで運ぶ

作成済みの PR への対応から始まったときは、手順 1〜4 を skip して手順 5 から始める。

1. diff を自分で読み直す。デバッグ出力、不要なコメント、依頼の範囲外の変更を除く
2. public repo（`gh repo view --json visibility` で確かめる）なら、`leak-scan` と `safe-to-publish` を通す
3. push と PR の作成は、kata の「自律と確認」に従う
4. PR の説明は、リポジトリの PR テンプレートがあれば必ずその見出しに沿って書く。何が変わり誰に効くか、どう確かめたか、レビューで見てほしい点を書く。UI の変更なら変更前後のスクリーンショットを貼る。言語は、public repo では英語、それ以外は日本語にする
5. CI とレビューコメントを見る。指摘は中身で判断し、直すか、理由を添えて見送る
6. stack の下の PR が merge されたら、上のブランチを新しい base に追従させ、コンフリクトを解消する
7. merge 後は、リリースとデプロイの完了を確かめ、本番のログや計測で変更が効いていることを確かめる。本番への適用（`terraform apply` など）や認証が要る操作は、ユーザーに手順を渡す
8. 片付ける。worktree とブランチの削除、issue のクローズ、ノートへの記録のうち、ユーザーがいつも求めるものを提案する

**返答**：PR の URL、CI の状態、残っている指摘、merge 後に確かめたこと。
