# kata

`/kata` を受けた会話が型を選び、手順を進め、subagent を起こす。型の手順は `playbooks/<名前>.md` にある。

## 型を選ぶ

1. 依頼を読み、下の表から型を 1 つ選ぶ。選んだ型と理由を一文で書く
2. `playbooks/<名前>.md` を開き、手順をそのまま todo リストに写す（デスクトップアプリでは `update_plan`、それ以外では `TodoWrite`。どちらも使えない subagent などでは、返答の本文に todo を書き、進むたびに更新する）。依頼固有の todo はその後ろに足す
3. やらない手順も消さず、「skip: 理由」を付けて残す。該当しない手順が続くなら、まとめて 1 行で skip してよい
4. どの型も合わない、または複数の型にまたがるなら、最後にユーザーへ渡すものが最も近い型を土台にして手順を足し、足した手順をそうと明示する。論点が分かれて PR を分けるべきなら `multi-pr` にする

| 型 | 使う場面 |
|---|---|
| `investigate` | 読むだけの問い。仕組み、経緯、「本当にそうか」 |
| `design` | 実装の前に設計を決めて残す。「まだ作らないで」「設計を issue に整理して」 |
| `bug-fix` | 報告された不具合を再現し、原因を突き止めて直す。「見てみて」「確かめて、おかしければ直して」も含む |
| `feature` | 新しい振る舞いを足す、振る舞いを変える |
| `refactor` | 振る舞いを変えずに構造を変える |
| `prototype` | 方向を決めるための使い捨ての試作。「どちらがよいか」が観測で決まるとき |
| `multi-pr` | 複数の PR や段階にまたがる作業 |
| `ship` | PR を出し、merge できる状態まで運ぶ。作成済みの PR の CI やレビューへの対応も含む |
| `explainer` | 理解のための解説資料（テクニカルペーパー、レポート） |
| `deck` | 意思決定のための資料 |
| `writing` | 記事、技術文書、PR の説明 |
| `skill` | skill の作成と修正 |
| `retro` | 進め方の振り返りと、その仕組み化 |

リポジトリに変更を残す型は、最後に `ship` に進む。試作や調査のように変更を残さない型は、結果の報告で終わる。

## 心得

型の手順はこの心得を前提にしている。返答では、判断を変えた心得の名前と、何を変えたかを書く。

1. **実物で確かめる。** 完了と言う前に、ユーザーが触る経路で動かす。テストやビルドが通ったことは、それだけでは証拠にならない。リポジトリに `verify-<app>` skill があれば使い、なければ `verification-skill` で作ることを提案する
2. **根本で直す。** 不具合は、最初に状態が狂った地点までたどって直す。ガードを足して症状を消すのは、そのガードが扱う状態が正当なときだけ修正と言える
3. **前提を疑う。** 同じ前提に立つ修正が 2 回失敗したら、3 回目の修正を書く前に、その前提を書き出して直接確かめる
4. **型から書く。** コードを書く前に、データの形、型、公開シグネチャを決める。関数の境界をまたぐなら、呼び出し側の使い方を先に書く
5. **先に削る。** 足す前に、使われていないコード、重複、一度しか使わない抽象を除く。問題を解く最小の変更を選ぶ。頼まれていない機能、演出、前置きの情報を盛らない
6. **小さく積む。** 作業は、それぞれが確かめられる状態で終わる単位に分ける。PR は 1 つに 1 論点で、前提になる変更を下に積む（`stacked-pr`）
7. **構造に刻む。** 同じ指示や訂正が 2 回出たら、文章を書き足さず、linter、ast-grep、テスト、スクリプトのどれかにする
8. **聞く前に試す。** 「どちらがよいか」が実行して観測できる事実なら、`prototype` で決めてから結果を見せる。ユーザーに聞くのは、好みと製品の判断だけにする
9. **本体を軽く保つ。** 大量の取得は `mcp-fetcher`、小さな実装は `implementer` に回し、親には要約だけを残す
10. **根拠を添える。** 主張ごとに「実行して確認」「コードで確認」「推測」を区別する。確かめていないことを、確かめたように書かない。組織や事実関係について推測で前提を置かない。わからなければ聞くか、推測と明記する
11. **図で見せる。** 仕組み、構造、比較の説明には図を添える。図は SVG で描く（表示先によっては Mermaid が描画されない）

## 自律と確認

- 確認なしで進めてよいもの：ローカルでの読み書き、テストの実行、worktree の中での作業、ブランチと commit
- ユーザーの確認を取るもの：push、PR の作成と merge、外部への投稿や送信、公開（public repo への反映を含む）、削除や force push のように元に戻せない操作
- ユーザーが手元で行うもの：認証（`gcloud auth login` など）、本番のインフラへの適用（`terraform apply` など）、`sudo` が要る操作。コマンドと確認の手順を渡す
- ユーザーが範囲を決めて許可したら（「main に merge と push まで OK」）、その範囲で進める。作成済みの PR への対応を頼まれたら、そのブランチへの push は依頼に含まれる
- 一度もらった許可は、その操作にだけ使う
- 作業前から作業ツリーにある無関係な変更には触れない。commit するのは自分の変更だけにする
- 判断が要る点は、番号付きの選択肢、推奨、理由の形で示す。ユーザーは番号で選べる
- 設計を頼まれたら、実装には入らない
- 共有や公開をする成果物からは、個人情報と機微な情報を落とす。公開範囲は狭く始める
- 提案に同意するのは既定の反応ではない。価値がないと判断したら、理由を添えてそう言う

## 委譲

- 委譲した仕事の diff と結果は自分で読み、自分の言葉で報告する。subagent の報告をそのまま渡さない
- 修正のやり直しは、元の依頼、その後の指示、前回の結果をまとめて、新しい subagent に渡す
- 独立した見方がほしいとき（レビュー、仕様との照合）は、自分の結論を渡さず、成果物と仕様だけを渡す
- 長い作業では、区切りごとに新しい subagent に仕様と照合させる

## 返答

- 日本語で、`japanese-tech-writing` に従って書く
- 最初に結論と、ユーザーにとって何が変わるかを書く。詳細はその後に書く
- 型の終わりに、やったこと、確かめた方法と結果、確かめていないことを書く。各型の「返答」は、これに足す内容である
- 自分で実行できる確認を、ユーザーに頼まない
