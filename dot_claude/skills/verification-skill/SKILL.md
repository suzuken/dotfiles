# 検証 skill の作成と保守

エージェントが自分の仕事を実物で確かめられないかぎり、人間が確認役として残り続ける。
検証 skill はその確認をエージェントの側に移すための道具であり、リポジトリの
インフラとして保守する。単体テストが示すのは分岐の振る舞いであって、ユーザーが
触る経路で動くことではない。

対象リポジトリに `.claude/skills/verify-*/` がなければ「作成」、あれば「保守」を行う。
生成物は、何も知らないエージェントが作業の途中で初めて読む前提で書く。

## 作成

### 1. 人ではなくリポジトリに聞く

次の 5 点をコードベースから答える。ユーザーに聞くのは、観測できないことだけにする。

| 問い | 調べること |
|---|---|
| 操作の入口 | ユーザーが触るもの（Web UI、CLI/TUI、デスクトップアプリ、API、モバイル、ライブラリ）。複数あれば主を 1 つ決め、残りは記録する |
| 起動 | リポジトリ自身の開発用コマンド（package scripts、justfile、Makefile、README）。ポート、環境変数、seed データ、認証 |
| 操作 | プログラムから操作する手段。既存の Playwright のテストや PTY ヘルパー、debug port を優先し、なければ汎用の方法（Web は Playwright / CDP、CLI は tmux / PTY、API は HTTP、iOS は Simulator）を選ぶ |
| 観測 | 取れる証拠（スクリーンショット、端末の出力、レスポンス、ログ、終了コード、DB の状態） |
| 隔離 | 2 つのインスタンスを並べて動かせるか（ポート、データディレクトリ、プロファイル）。できないなら、ユーザーの使っているインスタンスを操作しないことを生成物に明記する。既存のテスト設定や開発サーバが固定ポートを使っているなら、それとぶつからないポートを選び、生成物に書く |

checkout がそのままビルド・起動できないなら、先に直すか、何が壊れているかを正確に報告する。
壊れた土台の上で書いた skill は、誤った手順を教える。
検証と無関係な欠損（API が配信しない静的ファイル、サンプル設定など）が起動を妨げるなら、生成する skill の中で検証用の足場として作り、そう明記し、片付けで消してよい。

### 2. 操作 CLI を作る

エージェントが毎回使い捨てのスクリプトを書く代わりに、コマンドを 1 回叩けば済むようにする。
トークンが減り、手順が再現でき、CLI 自体をテストできる。
置き場所は `.claude/skills/verify-<app>/scripts/control-<app>`（実行権限つき）とする。

最初は小さく始める。`doctor`、主要な 1 機能の操作、証拠の取得（`snapshot` / `screenshot` など）で足りる。
ブラウザの中の状態のように、コマンドをまたいで持ち越す状態があるなら、常駐プロセス（CDP で接続したままのブラウザなど）を `up` / `down` で管理し、その PID とポートを記録ファイルに残す。各コマンドは記録ファイルから接続し直す。
エージェント向けの CLI として、次の性質を持たせる。

- 組み合わせやすい。少数のコマンドに機能をまとめ、呼び出しの連鎖を短くする
- 破壊的な副作用を持つコマンドには `--dry-run` を付ける
- サブコマンドで機能を段階的に見せ、一度に全部を出さない
- エラーメッセージに、次に何をすべきかを書く
- `--help` を充実させる
- 結果を機械可読な形式（JSON）で返す

### 3. SKILL.md を書く

`.claude/skills/verify-<app>/SKILL.md` を、frontmatter（`name: verify-<app>` と、アプリ名・操作の入口・使う場面を書いた `description`）付きで書く。
各節は手順 1 で実際に調べた内容に基づかせ、プレースホルダーを残さない。

- **起動**：検証用にアプリを起動するコマンドと、準備ができたことの見分け方（ログの行、プロンプト）。空のデータディレクトリから、マイグレーションと seed を含めて「使える状態」まで到達させる。永続データのないアプリなら、操作の起点になる初期状態（例: ゲームの初期盤面）を定義し、毎回そこへ戻す手段を用意する。プロセスが応答するだけでは準備完了ではない。短命な CLI なら、ビルドを 1 回行い、操作ごとに隔離した PTY / tmux セッションを起こすことを起動とする
- **doctor**：「このインスタンスは操作してよいか」に答える読み取り専用のチェック。プロセス、ビルドの版、ポートの持ち主、認証を確かめる。何かがおかしいと感じたら最初にこれを実行する
- **操作**：このリポジトリの実際のセレクタやコマンドで書く。座標やタブ順より、ARIA の名前、data 属性、プロンプト文字列、ルートのパスなど安定した手がかりを使う。安定した手がかりがない要素は、クラス名や位置での特定を操作 CLI の内部に閉じ込め、CLI の引数は意味の単位（行と列、ボタンの名前）にする。プロダクト側に手がかりを足すほうがよければ、提案として報告する
- **証拠**：何をどこに残すか。保存先は git にコミットしない場所にし（例: `.verify-evidence/` を `.gitignore` に追加する）、SKILL.md に明記する
- **片付け**：この実行が起動したものだけを止める。プロセス名で kill しない。片付けは証拠を消さない
- **helper**：同梱するスクリプトは実行可能にし、呼び出し方を本文に書く

証拠の基準も SKILL.md に書き写す。

- 実際のユーザー経路を通す。内部の setter やテスト専用のエンドポイントで代用しない
- 最終画面だけでなく、操作とその結果の状態の両方を残す
- 見た目に加えて、副作用（書かれたファイル、追加された行、送信されたメッセージ）を確かめる
- mock は、本番でもすでに境界で切り離されている外部系にだけ使う
- dry-run やテストモードは名前を信用しない。ネットワークや git ref を観測して、実際に何を省いているかを確かめる

### 4. Feature Map を作る

`.claude/skills/verify-<app>/features/README.md`（索引）と、ユーザーから見える機能ごとのファイルを作る。
最初はルート、コマンド、メニュー、ドキュメントから見つけた主要な 3〜5 機能で足りる。
形式は [references/feature-map-template.md](references/feature-map-template.md) に従う。

Feature Map は、コードベースのうち検証に要る部分だけをユーザー視点で圧縮した索引である。
エージェントは毎回コードを読み直さずに、機能への到達方法と操作手順を引ける。

seed データが利用手順の前提を満たさないなら、その手順は失敗として報告し、理由を「落とし穴」に書く。
手順を緩めて通すわけにはいかない。
前提が操作の流れ次第で起きたり起きなかったりする機能（例: 対局中のパス）は、ユーザーの経路で確実にそこへ至る手順の列を探して書く。見つからなければ、到達条件が非決定的であることを「落とし穴」に書き、未検証として扱う。
Feature Map が機能の入口を複数挙げているなら、都合のよい入口を 1 つ通しただけでは証明は不完全である。

### 5. 一度通しで実行して証明する

生成した skill の手順どおりに、起動、doctor、Feature Map の 1 機能の操作、証拠の取得、片付けまでを実行する。
片付けの後に、証拠が明記した場所に残っていることを確かめる。
失敗したら直し、失敗した試行のたびに片付けも実行して、プロセスやポートを取り残さない。
実行していない skill は下書きであり、成果物ではない。

本番と異なる代替環境（VM の代わりのコンテナ、リモートの代わりのローカル）で証明した場合は、
代替環境が行い本番では行われない準備手順をすべて列挙する。それらは本番で実行するまで未検証のまま残る。

### 6. 引き渡す

生成したファイル、通し実行の結果と証拠の場所、未検証の項目を報告する。手順 5 で動かしたのは 1 機能だけなので、Feature Map のうちまだ実行していない機能は、未検証として機能名で列挙する。
アプリが変わるたびに Feature Map はずれていくので、下の「保守」を回すよう伝える。

## 保守

アプリが変わると Feature Map はすぐにずれる。保守では、すべての機能ファイルをソースから確かめ、
すべての機能を実機で一度は動かす。厳密さの単位は機能であり、記述の 1 行ずつではない。

結果は次のどれかとして報告する。

- **clean**：全機能をソースと実機の両方で確かめ、直すものがなかった。ブランチも PR も作らない
- **changed**：証明できた修正を 1 本の PR にまとめた
- **blocked**：確認を終えられなかった、または修正を安全に出せなかった。何に阻まれたかを具体的に書く

編集してよいのは検証 skill のディレクトリ（SKILL.md、`features/`、同梱スクリプト）だけである。
保守の途中でプロダクトのコードは直さない。Feature Map に書かれた振る舞いをアプリがしなくなっていたら、
それは記述のずれ（Map を直す）か、プロダクトの退行（報告する）のどちらかであり、文書で覆い隠さない。

0. **対象を決める。** 起動・操作の節と Feature Map を持つ `.claude/skills/verify-*/` を探す。複数あれば、どれかをユーザーに聞く。なければ「作成」に切り替える
1. **索引を整える。** `features/README.md` と同じディレクトリのファイルを突き合わせ、欠落・余分・重複・リンク切れを直す
2. **ソースを読む。** 機能ファイル 1 つにつき、読み取り専用の subagent（`Explore`）を 1 体、並列で出す。各 subagent はその機能の仕組みをソースから説明し、記述のずれを引用つきで指摘し、実機で確かめる手順を 1 つ返す。アプリを操作させたり、ファイルを編集させたりはしない
3. **突き合わせる。** すべての機能ファイルに報告が返ったことを確かめる。手順をまとめて、必要なアプリの状態を少なくする。指摘されたずれは抜き取りで確かめる。最近の変更から Feature Map にない機能を探す。ないと判断するには、ソースの具体的なパスを示す
4. **実機で通す。** ソースが問題なさそうに見えても省略しない。操作は親がすべて自分で行い、起動の方式は検証 skill の「起動」節に従う。全機能を最低 1 回動かし、どんな失敗が起きても次の 3 つを守り通す
   - doctor を通していないインスタンスは操作しない。最初の操作の前、セッションを新しく起こすたび、操作が失敗した後に doctor を通す。doctor で見えない異常（プロセスは健全だが UI が固まっている）なら、既知の状態に戻すか再起動する
   - それまでに取った証拠は、どの片付けの後でも残っている。名前を付けた場所で実際に確かめる
   - 操作で起動したものを、その操作の用が済んだ後に残さない。失敗した試行の残骸も片付ける。共有のインスタンスでは、インスタンスではなく残骸だけを片付ける

   doctor の失敗が検証 skill 側のずれによるものなら、編集範囲の中で直して 1 回だけ再試行する。到達できない機能は、具体的な前提（認証、権限、OS、外部の状態）と試した経路を添えて「到達不能」と記録する。その前提が Feature Map に書かれていなければ、それもずれである。最後の片付けは、修正の再確認を含むすべての操作が終わった後に行う
5. **振り分ける。** ユーザー視点の記述が誤っている、または足りない場合は記述のずれとして直す。動いている振る舞いを操作 CLI で扱えない場合は CLI の不足として直す（直した CLI は実機で再度動かしてから出す）。アプリの振る舞いが実際に壊れている場合はプロダクトの不具合として報告し、この PR には含めない
6. **出すか止めるか。** changed なら、変更したファイルを読み直してから 1 本の PR にまとめる。clean と blocked では PR を作らず、結果と確認した範囲をそのまま報告する

実行メモ（確認した機能、到達不能の前提、確かめたずれ、結果）は作業用の場所に残し、コミットしない。

## 検証 skill の使い方

- **機能開発**：「verify-<app> で動作を確かめ、スクリーンショットを証拠として見せて」と頼む
- **バグ修正**：修正の前に、症状が出る入口（UI・CLI など）で同じ経路を再現する。修正後に同じ経路で通ることを確かめる。別の入口での確認は合格にしない
- **性能改善**：変更前のベースラインを先に測り、変更後と同じ手順・同じ回数で比べる
